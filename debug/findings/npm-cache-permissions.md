# npm cache permission isolation

- Symptom: a release dry run failed with npm `EPERM` before packaging because the user's default `~/.npm` cache contained root-owned entries. The project source, lockfile, and candidate archive were not the cause.
- Root cause: npm uses a shared user cache unless each invocation selects another cache. Historical `sudo npm` activity or an unrelated tool can therefore make a clean, user-level Skill installation depend on global filesystem ownership it does not control.
- Safety impact: asking the student to run `sudo`, recursively `chown` a home-directory cache, or change global npm configuration would exceed the Skill's installation scope and could affect unrelated projects.
- Downstream containment: the POSIX and PowerShell bootstraps select an npm cache below the isolated `SUSTECH_ADVISOR_INSTALL_ROOT` for registry lookup, consumer installation, and runtime audit. The setting is process-scoped, the POSIX directory is mode `0700`, and neither bootstrap reads from or repairs the user's global npm cache.
- Validation evidence: the `v0.2.6` candidate passed `npm pack --dry-run --ignore-scripts` with a private task cache after the same command failed against the pre-existing global cache. A real Darwin arm64 POSIX bootstrap then installed 105 packages from the candidate archive with the pre-existing global cache left untouched, created its own cache at mode `0700`, completed its installed-tree audit and doctor gate, and passed all 30 applicable packaged tests (the Windows-only test skipped). Public `v0.2.6` and `v0.2.7` Release smoke subsequently exercised the real POSIX and PowerShell bootstraps on macOS, Ubuntu, and Windows. An independent public v0.2.7 Darwin arm64 install again created the dedicated cache at mode `0700`, installed 105 packages, and completed its installed-tree audit without reading or repairing the global cache. Repository validation rejects either bootstrap if its isolated-cache binding is removed.
- Maintenance rule: contain npm cache failures inside the selected installation root and retry once after identifying the permission signature. Never use `sudo`, `chown`, or a global `npm config set cache` as automatic remediation, and never classify a local cache permission failure as a registry, proxy, or package-integrity failure.
