# Upstream fork CI can wait for maintainer approval

- Symptom: upstream `sustech-cli` PRs #8 and #10 are mergeable, but their check rollups are empty and GitHub reports `mergeStateStatus: UNSTABLE`.
- Root cause: GitHub created [Actions run 33559383724](https://github.com/wormforce/sustech-cli/actions/runs/33559383724) for PR #8 head `7ce36b6` and [run 33626389782](https://github.com/wormforce/sustech-cli/actions/runs/33626389782) for PR #10 head `ea7108a`, then completed both as `action_required` before creating any jobs. This is a workflow-approval state, not a test conclusion; only an upstream maintainer can start the matrices.
- Safety impact: treating an empty rollup as a passing check could allow an unverified credential, mutation, selection, or privacy change to be merged; treating it as a test failure could prompt misleading fixes or repeated no-op pushes. The approval state itself does not execute campus reads or mutations.
- Downstream containment: the advisor records the upstream gate separately from test results, keeps its local compatibility, timeout, and privacy guards enabled, and does not claim that either PR passed upstream CI or was merged. Its GitHub Release remains pinned to the reviewed published `sustech-cli` interface while the upstream patches are pending.
- Upstream owner: [`wormforce/sustech-cli#8`](https://github.com/wormforce/sustech-cli/pull/8) and [`wormforce/sustech-cli#10`](https://github.com/wormforce/sustech-cli/pull/10); a `wormforce/sustech-cli` maintainer owns approval of the external-fork workflows and the eventual review and merge decisions.
- Local evidence: on PR #8 head `7ce36b6` and base `8efad42`, type-checking passed, all 326 tests passed when the existing public-calendar integration source was reachable, the runtime audit found zero vulnerabilities, and the package dry run contained 297 files. On PR #10 head `ea7108a` and the same base, type-checking passed, all 314 tests passed with public network access, the focused Keyring suite passed 10/10, the runtime audit found zero vulnerabilities, the package dry run passed, and a synthetic nonexistent macOS Keychain account returned status in 0.28 seconds. No personal campus read or mutation was performed by either upstream suite.
- Test/fixture evidence: reproduce the GitHub gates with `gh run view 33559383724 --repo wormforce/sustech-cli --json status,conclusion,jobs,headSha` and the equivalent command for run `33626389782`; both report `completed`, `action_required`, their expected head, and an empty job list. Reproduce the code checks from each exact head with `npm run check`, `npm test`, `npm audit --omit=dev --audit-level=low`, and `npm pack --dry-run --ignore-scripts --json`. No campus fixture is needed for the approval-state check; the suite uses repository fixtures, except for the pre-existing public-calendar integration source described below.
- Test-environment finding: the existing upstream test `context live supports calendar level and degrades gracefully when credentials are unavailable` still downloads the public SUSTech calendar. A network-restricted run fails that one test with `NETWORK_ERROR`, while the same no-credential command passes when only the public source is reachable. This test predates PR #8 and is not evidence of a credential, selection-contract, or privacy regression.
- Maintenance rule: inspect the Actions run itself before treating an empty check rollup as green or red. For `action_required`, send one precise approval request and wait; do not repeatedly rerun, push no-op commits, or claim CI passed. For local restricted-network validation, report the public-source precondition separately from the hermetic unit-test results.
