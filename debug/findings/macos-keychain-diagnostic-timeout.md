# macOS Keychain status can stall diagnostics

- Symptom: in a full macOS host context, public `sustech-cli@0.10.0` can leave `sustech auth status --profile default --json` waiting indefinitely while the same advisor doctor returns quickly in a Keychain-inaccessible sandbox.
- Safety impact: an unbounded doctor or diagnose blocks maintenance, can leave users unsure whether to retry login, and prevents the sanitized diagnostic from being written. Repeated manual retries may cause more credential-store prompts without improving state.
- Downstream containment: every environment probe and optional live auth check now has a ten-second subprocess limit. A whole-command stall becomes `COMMAND_TIMEOUT`; a successful upstream status carrying a bounded helper failure is projected as `CREDENTIAL_STORE_TIMEOUT` into doctor and sanitized diagnostics. Installation readiness remains independent from authentication readiness, and neither path retries or suggests login automatically.
- Upstream owner: the underlying Keychain status stall belongs to `sustech-cli`; the advisor owns the bounded-call contract at its process boundary.
- Upstream remediation: [wormforce/sustech-cli#10](https://github.com/wormforce/sustech-cli/pull/10) separates existence-only status checks from password reads, uses macOS `security find-generic-password` without `-w`, bounds credential-helper processes to five seconds, and projects `CREDENTIAL_STORE_TIMEOUT` without retry. Commit `ea7108a` passed typecheck, 314/314 tests, prepack dry-run, a zero-vulnerability production audit, and a synthetic macOS host probe in 0.28 seconds. The PR is still pending upstream review and CI approval, so the downstream ten-second containment remains required.
- Evidence: injected never-settling auth-status and auth-check fixtures prove that doctor returns promptly, retains a compatible installation state, marks authentication not ready, and emits only `COMMAND_TIMEOUT`. The real hanging process was terminated before any support bundle was written.
- Release observation: the first read-only `v0.2.4` live doctor returned upstream auth-check exit code 2, while a direct bounded auth check immediately succeeded and one subsequent live-doctor run passed with the same Keychain credential. Treat one bounded failure as a transient observation rather than proof that credentials expired; do not loop or trigger login automatically.
- Current Release observation: public v0.2.8 queried the real `macos-keychain` through its sibling-bound CLI with backend and credential availability true. A process-scoped inherited-route read-only live doctor then reached `COMMAND_TIMEOUT` in 10.70 seconds; v0.2.7 and a same-condition v0.2.6 comparison also timed out, while an earlier comparison had passed in 1.744 seconds. This isolates the current result to the intermittent TIS/CAS route rather than the launcher selection, bounded process runner, or expired local credentials.
- Maintenance rule: all new upstream calls must use the bounded runner, not only environment or credential probes. Preserve status-only Keychain checks, separate credential readiness from a transient live network gate, and never add an unbounded direct `runSustech` call.
